# 智能对话文书生成质量升级设计

## 背景

当前智能对话中的文书生成虽然已经具备文书路由、Prompt 模板、法律检索和基础质量校验能力，但最终产物仍存在明显问题：

- 输出经常停留在“像文书”的程度，而不是“可交付使用”的程度
- 合同、诉状、律师函、法律意见书等不同文书类型的质量要求没有真正拉开
- 缺少对信息完整度的判断，信息不足时仍直接硬生成，导致内容空泛
- 质量校验过于宽松，很多极简文本会被当作合格结果返回
- 二次修复策略只做泛化补充，没有针对缺失项和文书类型做定向补写

这直接影响产品可信度：律师、企业法务、个人客户拿到结果后仍需要从头重写，无法把系统视为高质量起草助手。

## 目标

- 将文书生成从“简版回答”升级为“可继续交付使用的专业草案”
- 覆盖合同协议、诉讼文书、律师函/催告函、法律意见书等主要文书类型
- 在“尽量自动成稿”和“信息不足时显式保留待确认项”之间建立统一策略
- 提高结果稳定性，避免短文、空文、少条款、缺结构的结果直接返回
- 保持现有聊天入口、文档工作台和 Agent 架构基本不变，优先升级生成中枢

## 非目标

- 不重做前端聊天页整体交互
- 不引入新的模型供应商或新的推理基础设施
- 不把本次工作扩展为完整的文书表单化产品
- 不追求一步到位覆盖所有司法文书细分场景，只先建立高质量底座

## 方案结论

采用 **统一质量底座 + 文书类型专项规则 + 定向重写闭环**。

核心原则：

- 先判断“能否直接成稿”，再决定如何生成，而不是所有请求都走同一套 Prompt
- 先生成完整结构，再做缺口补强，而不是一次性要求模型自己兜底
- 质量校验要能区分“可用草案”和“不可交付结果”
- 信息不足时不装作已经定稿，而是明确输出待确认项、风险提示和起草说明

## 总体架构

### 生成链路

推荐将现有文书起草链路升级为五段式：

1. **文书识别**
   - 识别文书类型、业务场景、适用角色、风险级别
2. **信息完整度评估**
   - 判断用户提供的信息是否足以直接出成稿
3. **结构化起草**
   - 按文书类型生成完整结构和核心正文
4. **质量校验**
   - 用更严格的规则检查结构、实质条款、事实位、救济路径、签署区等
5. **定向补写**
   - 按校验缺项进行二次重写或局部补强，再输出最终文书

### 三态输出策略

系统不再默认只有一种输出，而是根据完整度与质量分数落到三种结果：

- **成稿**
  - 适用于事实明确、主体明确、交易条件或争议请求明确的场景
  - 输出完整正文，可直接交付律师或业务人员继续审阅
- **高可用草案**
  - 适用于主要信息已具备，但个别关键字段缺失
  - 输出完整框架和主要条款，同时保留必要占位，并附“待确认事项”
- **结构化草稿**
  - 适用于事实信息严重不足、法律路径不明或用户意图过于模糊
  - 输出完整专业骨架，但显式说明哪些信息缺失，避免伪成稿

## 模块设计

### 一、起草策略层

在 `DocumentDraftAgent` 上增加起草策略层，用于决定生成路线，而不是直接拼一个长 Prompt 发给模型。

建议新增或内聚以下职责：

- `doc_type` 归一化
  - 统一合同、协议、起诉状、律师函、法律意见书等类别判断
- completeness 评分
  - 评估当事方、标的/争议焦点、金额、时间、履行义务、请求事项、证据要点等关键信息是否齐全
- draft mode 决策
  - 按评分决定输出成稿、高可用草案、结构化草稿
- generation brief 组装
  - 把文书目标、用户事实、缺失信息、必须条款、风险条款、适用法条整理成模型更易执行的任务单

### 二、专项文书规则层

不同文书不能再只靠一套公共 Prompt + 少量结构提示。

建议建立统一注册表或规则映射，为每一类文书定义：

- 必备结构
- 必备事实位
- 必备法律分析位
- 必备风险条款
- 最低字数与最低段落数
- 允许的占位符类型
- 需要附带的“待确认事项”格式

优先覆盖四大类：

- **合同/协议类**
  - 强化当事方、鉴于条款、标的、价款、履行、验收、违约责任、争议解决、通知送达、签署区
- **诉讼文书类**
  - 强化原被告信息、诉讼请求、事实与理由、证据指向、法律依据、法院尾部格式
- **律师函/催告函类**
  - 强化委托关系、事实陈述、法律分析、履行要求、期限、后果警示
- **法律意见书类**
  - 强化委托范围、事实前提、分析框架、结论、保留意见、适用限制

### 三、Prompt 结构升级

现有 Prompt 偏“告诉模型你要专业”，缺少“告诉模型该如何一步一步写”。

建议改造成四段式 Prompt：

- **角色约束**
  - 明确专业角色、适用边界、禁止空泛表达
- **起草任务单**
  - 明确文书类型、使用目的、当事方、场景事实、关键变量、缺失位
- **输出规格**
  - 明确标题层级、段落结构、占位规则、法条引用规范、落款规范、附录规范
- **质量底线**
  - 明确禁止极简、禁止省略核心条款、禁止用泛泛提示替代正文、禁止在关键信息不足时伪装成定稿

其中最关键的变化是：

- 对模型显式说明当前是“成稿”还是“高可用草案”
- 当信息不足时，要求保留专业可编辑占位，不允许只写“请根据实际情况补充”
- 对需要用户补充的事实，单独输出“待确认事项”而不是散落在正文中

## 质量闸门设计

### 一、统一评分维度

现有质量校验主要偏字数和简单结构检查，需要扩展为更接近专业文书的评分模型。

建议统一维度：

- **结构完整度**
  - 是否具备该类型文书的标准段落和结束部分
- **事实充实度**
  - 是否具备核心事实位，而不是只写原则性套话
- **条款实质性**
  - 合同条款是否具体到条件、期限、责任、金额、违约机制
- **法律支撑度**
  - 是否出现相应法条、法律依据或规范性分析
- **可交付性**
  - 是否可以直接交律师/业务方继续使用，而不是只能当思路参考

### 二、分类阈值

不同文书应设置不同闸门：

- **合同/协议**
  - 字数、条款数、签署区、当事方、违约责任、争议解决缺失时直接判定为不通过
- **诉状/申请书**
  - 原被告、请求事项、事实理由、法院尾部缺失时直接不通过
- **律师函**
  - 致函对象、委托说明、履行要求、期限与后果缺失时直接不通过
- **法律意见书**
  - 缺事实前提、缺分析框架、缺结论或缺特别说明时不通过

### 三、定向补写机制

二次修复不再只给一句“请补充修正”，而是基于验证结果生成补写任务。

补写任务要明确：

- 缺了什么
- 缺失为什么影响可交付性
- 需要补到什么程度
- 保留原文哪些信息
- 最终仍需输出完整文书而非片段

当首次结果质量过低时，优先：

- 重新生成整篇
- 继承已识别的场景事实和法律依据
- 把缺失项、最低条款数、必备结构一次性喂回模型

## 输出格式设计

### 文书正文

正文继续使用 Markdown，以兼容现有前端文档面板和画布识别逻辑。

统一格式要求：

- 标题使用一级标题
- 主体结构使用二级标题
- 同类条目使用稳定编号
- 保留专业占位符时使用统一中括号或全角括号规范

### 附加区块

正文后统一追加标准附加区块：

- `---`
- `起草说明`
- `待确认事项`
- `使用提示`

这三个区块的职责分别是：

- **起草说明**
  - 解释关键条款设置或法律路径选择
- **待确认事项**
  - 列出仍需用户或律师确认的信息
- **使用提示**
  - 提醒该文书是否需要结合证据、附件、盖章、授权、送达方式等进一步处理

## 风险点

- 质量门槛提升后，部分历史上“能返回就算成功”的请求会变成草案态或补写态
- Prompt 变长后，弱模型可能更容易丢失后半段约束
- 多轮补写会增加一定延迟，需要平衡质量与响应速度
- 文书类型判断若不稳定，可能导致套错结构规范

## 验证方案

### 样例验证

至少准备以下样例集：

- 合同类：服务合同、租赁合同、股权转让协议
- 诉讼类：民事起诉状、财产保全申请书
- 函件类：律师函、催告函
- 意见书类：法律意见书、尽调结论摘要

每类样例分别覆盖：

- 信息完整
- 信息部分缺失
- 信息严重不足

### 验证标准

- 不再出现明显极简短文直接通过
- 信息完整时应输出接近可交付成稿
- 信息不完整时应输出完整草案并显式列出待确认项
- 校验未通过时应触发定向补写，而不是原样返回
- 结果仍能被前端识别并进入文档工作台

### 回归验证

- 聊天文书起草链路可正常返回
- 独立文档生成接口可正常保存文书
- 非文书类聊天不会被误伤
- 基础测试与类型检查通过

## 实施顺序建议

1. 收紧并分类化文书质量校验
2. 改造文书起草 Prompt 为任务驱动结构
3. 在 `DocumentDraftAgent` 中加入完整度评估和三态输出
4. 增加定向补写闭环
5. 统一聊天入口与独立文档接口的生成逻辑
6. 用样例集做回归验证并微调阈值

## 结论

本次升级的重点不是“把文书写长”，而是把文书生成从一次性文本补全，升级为一条面向交付质量的起草流水线。

最终应达到三个判断标准：

- 用户拿到的不再是极简模板，而是可继续使用的专业草案
- 系统能够区分“可以成稿”和“只能草案”，不再伪装完成度
- 生成质量的提升来自流程、规则和校验闭环，而不只是堆 Prompt
