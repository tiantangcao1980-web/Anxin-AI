# 多端客户端设计

## 背景

当前仓库已经具备多端基础：

- Web 前端基于 React + Vite
- 桌面端已存在 Tauri 2.x 工程
- 前端已存在 Tauri bridge 与多平台脚本
- CI 已具备桌面端与移动端构建雏形

因此本次目标不是从零创建新客户端，而是在现有基础上完成产品化设计，优先落地桌面端，同时为移动端建立可持续演进路径。

## 决策结论

采用 B 方案：

- 桌面端继续使用 Tauri
- 移动端单独使用 React Native + Expo
- Web、桌面端、移动端共用同一后端协议、业务 SDK、类型定义与同步协议

不采用“一套 Tauri 同时覆盖桌面与移动 UI”的原因：

- 桌面端适合复用现有 Web UI 与 Tauri 原生能力
- 移动端需要原生交互、推送、弱网、分享、相机、手势等能力
- 直接用 Web/Tauri Mobile 容易在移动端形成体验上限

## 总体架构

建议仓库逐步形成如下结构：

- `backend/`：统一 FastAPI 后端
- `frontend/`：Web 前端与桌面端共享 UI 基座
- `desktop/`：Tauri 桌面客户端
- `mobile/`：React Native / Expo 移动客户端
- `packages/` 或 `shared/`：共享类型、SDK、适配层、同步协议

架构分层如下：

1. 后端能力层  
   提供统一的鉴权、组织、合同、文档、协作、消息、知识检索、AI 能力与同步接口。

2. 共享协议层  
   定义三端一致的数据模型、错误模型、分页结构、上传协议、同步状态与事件结构。

3. 共享业务 SDK 层  
   对后端 API 做统一封装，避免三端分别拼接请求与解析响应。

4. 平台适配层  
   对存储、文件、通知、网络状态、更新、分享、系统能力提供统一抽象。

5. 页面与交互层  
   Web / Desktop 共用大部分页面逻辑；Mobile 独立构建原生页面，但复用共享协议和业务 SDK。

## 桌面端设计

### 目标

第一优先级是做出可安装、可同步、可使用本地能力的 macOS 与 Windows 桌面客户端，而不是简单网页壳。

### 第一版能力范围

首版桌面端包含以下能力：

- macOS 与 Windows 安装包
- 登录与组织切换
- 主导航与核心工作台入口
- 文件选择、上传、下载
- 系统通知
- 本地 SQLite
- 离线队列
- 手动与自动同步
- 本地 LLM 配置与基础调用
- 自动更新链路预留

### 模块划分

1. 应用壳层  
   负责窗口、托盘、深链、通知、菜单、更新。

2. 桌面工作台 UI  
   复用现有 React/Vite 主界面，优先覆盖高频链路，而不是要求所有 Web 页面一次性完全适配。

3. 本地数据层  
   使用 SQLite 存储登录态、用户偏好、最近访问、离线缓存、草稿、待同步记录、本地模型配置。

4. 离线队列与同步引擎  
   记录待发送消息、待同步批注、文档草稿、上传任务、本地 AI 处理结果等。

5. 本地 LLM 能力层  
   本地模型承担敏感内容摘要、临时问答、预分析、弱网辅助；重型推理继续依赖云端。

6. 平台差异层  
   处理 macOS / Windows 在路径、通知、深链、自启动、签名、更新方面的差异。

### 桌面端边界

首版必须优先完成“可安装 + 可用 + 可同步 + 本地增强”，以下内容后置：

- 全量离线知识库
- 全量本地向量索引
- 全部 Web 页面 100% 桌面专属优化
- 多窗口协同编辑增强
- 复杂系统级集成

## 移动端设计

### 技术选型

移动端单独新建 `mobile/`，采用 React Native + Expo。

选择原因：

- 与现有 React 团队栈兼容
- 推送、权限、文件、分享、相机等原生能力成熟
- 适合快速做出轻协作型移动产品

### 第一阶段定位

移动端第一阶段聚焦轻协作，不直接复制桌面工作台。

首批重点场景：

- 消息与会话
- 审批处理
- 任务收件箱
- 通知中心
- 文档查看、评论、批注
- 合同审查、尽调、知识检索的摘要页与快操作页

### 页面分层

1. 认证层  
   登录、组织切换、设备绑定、安全校验。

2. 收件箱层  
   聚合待审批、待处理任务、新消息、系统通知、AI 提醒。

3. 协作层  
   消息、文件会话、协作文档入口，优先优化语音输入、图片附件、推送跳转与快捷评论。

4. 业务快操作层  
   展示合同审查结论、尽调摘要、知识检索结果、风险提示，并支持评论、转发、指派、稍后处理。

5. 我的与设置层  
   个人信息、组织切换、通知设置、缓存管理、离线内容、安全设置。

### 差异化原则

- 桌面端强调深度生产、连续工作、复杂操作
- 移动端强调随时响应、轻决策、上下文接力

同一业务能力在两端不应使用同一套页面压缩实现，而应按设备场景重新设计交互。

## 共享层设计

### 共享类型与协议

建议抽离以下共享定义：

- 用户与组织
- 合同、文档、审批、任务
- 消息与会话
- 知识检索结果
- AI 任务状态
- 分页结构
- 错误码模型
- 上传协议
- 同步状态与同步事件

### 共享业务 SDK

建议按领域拆分 SDK：

- `auth-sdk`
- `contracts-sdk`
- `documents-sdk`
- `tasks-sdk`
- `messages-sdk`
- `knowledge-sdk`
- `sync-sdk`

目标是让 Web / Desktop / Mobile 统一通过 SDK 调用后端，而不是在页面层散落请求代码。

### 平台适配接口

建议抽象统一接口：

- 存储接口：Web localStorage / Tauri Store / Expo SecureStore
- 文件接口：浏览器 File API / Tauri FS / Expo FileSystem
- 通知接口：Web Notification / Tauri Notification / Expo Push
- 网络状态接口：浏览器在线状态 / Tauri OS / Expo NetInfo
- 深链与分享接口：平台侧各自实现，业务侧统一调用

## 数据流与离线同步

### 数据流策略

采用“云端主数据源 + 本地缓存 + 本地待同步队列”策略。

#### 只读型数据

例如合同列表、审批列表、组织信息、知识检索结果。  
流程：云端拉取 → 本地缓存 → 页面读取缓存 → 后台刷新。

#### 草稿型数据

例如批注、文档草稿、待发送消息。  
流程：本地写入 → 进入同步队列 → 后台上传 → 成功后标记已同步。

#### 实时协作型数据

例如消息、通知数、协作状态。  
优先使用 WebSocket / SSE；移动端允许降级为轮询或前后台切换补拉。

#### 本地 AI 型数据

例如本地摘要、分类建议、敏感内容预分析。  
默认先本地展示，再由用户决定是否回传云端。

### 同步模型

同步引擎统一使用事件队列模型，事件至少记录：

- 业务对象类型
- 本地 ID / 远端 ID
- 操作类型
- payload
- 重试次数
- 最近错误
- 创建时间
- 最后尝试时间

### 冲突处理

第一版采用分级冲突策略：

- 消息、评论、任务状态：追加型，直接重试
- 草稿文本：使用版本号或更新时间检测冲突
- 冲突时提供保留本地、覆盖远端、生成副本三种处理方式

### 用户可见状态

三端统一同步状态：

- 已同步
- 待同步
- 同步中
- 同步失败
- 存在冲突

桌面端可常驻状态栏；移动端在详情页或同步中心展示。

## 实施顺序

### 阶段 0：共享层整理

- 抽离公共类型
- 抽离统一 SDK
- 抽象平台接口
- 明确同步协议与错误模型

### 阶段 1：桌面端 MVP

- 打通 macOS / Windows 打包
- 跑通登录、导航、文件、通知、托盘
- 接入本地 SQLite
- 接入离线队列与同步状态
- 接入本地 LLM 基础能力

### 阶段 2：桌面端增强

- 优化弱网体验
- 增强自动更新
- 完善冲突处理
- 补齐桌面高频页面适配

### 阶段 3：移动端骨架

- 新建 `mobile/`
- 接入共享 SDK
- 跑通鉴权、导航、状态管理、推送、文件能力
- 完成收件箱、消息、审批、任务主链路

### 阶段 4：移动端业务扩展

- 文档查看与批注
- 合同审查摘要页
- 尽调摘要页
- 知识检索问答页
- 弱网缓存与同步增强

## 里程碑

### M1：共享层完成

- 三端不再散落拼接 API
- 公共类型与 SDK 可被复用
- 平台能力适配层成型

### M2：桌面端可发布

- macOS dmg 可安装
- Windows msi / exe 可安装
- 登录、导航、消息、任务、合同、文档、知识入口可用
- 本地数据、同步状态、本地 LLM 基础能力可用

### M3：移动端可内测

- Android 安装包可运行
- iOS TestFlight 可分发
- 收件箱、消息、审批、任务、通知主链路跑通

### M4：多端协同稳定

- 桌面端与移动端同步策略稳定
- 网络中断、恢复、重试、冲突处理可验证
- 关键主链路可重复测试

## 风险与约束

### 主要风险

- 共享层抽象不稳，导致三端逻辑分叉
- 桌面端首版范围失控
- 移动端误做成桌面压缩版
- 离线同步复杂度被低估
- 桌面签名、公证、移动证书和商店分发成为非代码阻塞点
- 对本地 LLM 能力抱有超出首版承载范围的预期

### 明确约束

- 首版桌面端必须收口到高频主链路
- 移动端第一阶段只做轻协作和摘要型专业能力
- 本地 LLM 作为增强层，不替代云端核心推理
- 同步模型先做可解释、可观测，再做更复杂的一致性增强

## 验收标准

### 桌面端验收

- macOS 与 Windows 均可独立安装
- 登录与核心导航可用
- 文件上传、下载、通知正常
- 断网操作可入队，恢复后可同步
- 本地 LLM 配置与基础调用可用
- 常见失败有清晰错误反馈

### 移动端验收

- Android / iOS 至少各有一条稳定分发链路
- 登录、组织切换、消息、审批、任务、通知、文档查看可用
- 推送可跳转到具体上下文
- 弱网场景下具备基础浏览与待处理能力

### 共享层验收

- 三端共用业务 SDK
- 三端共用核心类型定义
- 同一业务对象在三端语义一致
- 后端接口变更时不需要三端分别大改调用层

## 推荐落地结论

推荐执行路径为：

1. 先抽共享层
2. 先做桌面端可发布版本
3. 再做移动端轻协作版本
4. 最后逐步扩展移动端专业场景与桌面端深度能力

该路径同时满足以下目标：

- 优先交付 macOS 与 Windows 桌面客户端
- 保持移动端长期体验上限
- 降低三端并行演进时的重复开发成本
