# 本机运行与治理后台信息架构边界

> 日期：2026-05-09
> 状态：已采纳，后续开发按此边界执行

## 目标

让用户清楚区分两个入口，并减少“两个后台/两套设置”的误解：

- **我的设置**：我这个账号和这台设备如何使用产品。
- **本机运行**：我的这台设备如何运行。
- **治理后台**：组织和平台如何被治理。

这两个入口不能成为两套重复设置页。任何新功能进入前，先判断它属于“当前设备运行态”还是“组织治理态”。
最终产品口径是：工作站负责业务执行和本机运行，治理后台负责组织治理和平台配置；两者可以共享底层服务，但不能共享用户心智。

## 边界规则

| 维度 | 本机运行 | 治理后台 |
| --- | --- | --- |
| 主语 | 我、当前设备、当前运行时 | 组织、平台、管理员 |
| 数据范围 | 本机配置、只读状态、个人偏好 | 用户、角色、组织、审计、安全、计费、模型治理、系统集成、MCP/工具连接 |
| 典型动作 | 切换绝密/混合/云端模式、保存本机后端地址、本地模型默认项、发送本机通知测试 | 创建用户、授权角色、配置组织级模型、管理系统集成、查看审计和系统健康 |
| 凭据原则 | 不保存 API 密钥、Token、证书；只展示可用状态或本机无密配置 | 保存和治理组织级密钥，响应必须遮罩，审计必须脱敏 |
| 失败状态 | 本机不可用、需桌面端、待签名/真机证据 | 缺外部 API、缺沙箱联调、缺审批/审计证据 |

## 功能归属判定

- 影响当前桌面运行、当前用户效率或本机安全的功能，放在工作站或我的设置。
- 影响多用户、多组织、密钥、审计、计费、权限或系统接入的功能，放在治理后台。
- 同一个能力既有本机状态又有组织策略时，工作站只展示当前可用状态和跳转入口，治理后台承载配置、审批和审计。
- 移动端/uni-app 是随身助手、审批端和远程控制入口，不复制治理后台，也不承担桌面本机配置。

## 交互原则

- 本机运行只放“立刻影响当前桌面端”的控件。
- 本机运行可以展示组织能力状态，但复杂配置跳转治理后台或 Agent 治理工作台，不在本机页重复编辑。
- 治理后台不展示本机探针、不做本机运行模式切换。
- 相同底层 API 可以复用组件，但 UI 文案必须明确当前作用域。
- 名称避免混淆：前台为“我的设置 / 本机运行 / 通知偏好”，后台为“治理后台 / 治理总览 / 模型治理 / 系统集成 / Agent 治理”。

## 当前落地

- 设置页标题保持“我的设置”，说明其处理个人账号、本机运行和当前账号可用连接。
- 原“桌面工作站”可见入口收束为“本机运行”，面板主标题改为“本机运行控制台”，内部只保留本机运行配置、本地模型、本机通知、离线队列和只读探针。
- 治理后台入口保持“治理后台”，总览改为“治理总览”，平台基础页避免再使用“基础设置”这种与个人设置混淆的名称。
- E2E 同步锁住新的入口文案，避免后续又退回模糊命名。
- 模型连接 CRUD 已保留在治理后台“模型治理”；MCP/工具连接 CRUD 已迁入治理后台“系统集成”；我的设置不再承载组织级 LLM/MCP 凭据 CRUD。
- 本机运行页里的 Skills/MCP 卡片只作为治理状态入口，不再指向个人设置里的重复 MCP 配置页。
