# 2026-05-08 外部智能体项目能力借鉴分析

> 目的：分析 Hermes Agent、OpenClaw、HiClaw、DeepTutor、CLI-Anything、RAG-Anything、browser-use、Scrapling 的可借鉴能力，补充安心 AI 的全设备智能助手定位。
> 口径：只吸收产品/架构模式，不直接复制外部代码；引入依赖、协议或抓取能力前必须另走安全、许可证、合规和隐私审查。

## 2. 能力吸收后的产品升级方向

| 能力域 | 当前定位 | 升级后定位 | 企业治理要求 |
|---|---|---|---|
| 法务/财务/税务/风控 | 行业专用 AI 平台 | 仍是项目核心差异化入口 | 高风险结论必须有依据、免责声明和专业人士转介 |
| 通用工作助手 | 当前偏弱 | 覆盖写作、总结、制度问答、报告、培训材料、会议纪要、任务拆解、定时提醒 | 默认只能使用基础能力和组织授权知识库 |
| 软件/原型开发 | 当前未列为核心 | 可让用户生成内部小工具、流程原型、表单、数据脚本、CLI 自动化和设计原型 | 只能在沙盒执行；发布、联网、读写敏感数据需老板/超级管理员审批 |
| 浏览器与网页任务 | 当前主要用于尽调/爬虫 | 升级为“可控浏览器执行器”：填表、下载材料、公开资料核验、网页截图留痕 | 禁止静默提交高风险表单；所有操作留痕、可回放、可撤销 |
| 多模态知识库 | 当前以文档/RAG 为主 | 支持 PDF、Office、图片、扫描件、表格、公式、图表、票据和网页证据 | 知识库按个人/组织/项目/客户/本地分层，绝密模式默认不出站 |
| Skills/MCP/CLI 工具 | 已有底座 | 升级为组织可管理的能力市场和工具执行层 | 能力上架、启用、禁用、调用、失败、越权都必须审计 |
| 多通道/多设备 | 已定位桌面/移动 | 桌面主工作站 + 移动远控 + 消息入口 + 定时任务 | 设备配对、通道 allowlist、命令过期、撤销和沙盒隔离 |

### 2.1 Codex / Claude 可借鉴的交互体验

Codex 和 Claude 对本项目最值得借鉴的不是某个具体界面，而是“可信 AI 工作台”的交互原则：

| 交互原则 | 含义 | 对安心 AI 的落点 |
|---|---|---|
| 过程透明 | 长任务展示计划、当前步骤、工具状态、失败原因和下一步 | 合同审查、尽调、桌面远控、软件原型和专业材料包生成都要有任务时间线 |
| artifact-first | 结果不是一段聊天，而是可编辑、可引用、可导出的文件/报告/原型/脚本 | 合同、制度、报告、材料包、原型和数据脚本进入 artifact store |
| 用户可掌控 | 用户能打断、恢复、修改方向、接管执行 | 移动远控桌面、浏览器执行、CLI 和高风险 agent 工作室必须支持暂停/接管/终止 |
| 上下文连续 | 同一事项跨设备、跨会话、跨模型仍保留任务状态和引用 | 桌面主工作站 + 移动随身助手要共享任务状态、审批状态和未完成动作 |
| 能力可发现 | 命令面板、上下文建议和能力中心让用户知道系统能做什么 | Skills/MCP/模型/知识库/专业转介用能力中心统一呈现 |
| 谨慎表达 | 高风险结论标明依据、边界和需要专业确认的部分 | 法务、财税、舆情和政府试点场景必须避免过度自信 |

这些体验必须和权限治理绑定：越强的能力越要清楚展示影响范围、数据范围、审批状态、审计入口和撤销方式。

### 2.2 Skills 进化与智能体自我改进

Hermes Agent 的 Skills/记忆、自改进方向与 CLI-Anything 的 Skill/CLI 生成能力值得吸收，但企业版必须从一开始治理化：

| 生命周期 | 要求 |
|---|---|
| 创建 | Skill 必须声明 owner、版本、输入输出 schema、风险级别、依赖、可访问数据域和默认禁用/启用状态 |
| 学习 | 智能体可以从失败案例、用户反馈、审计日志和评测结果生成改进建议 |
| 评测 | 每次升级必须通过功能评测、权限回归、prompt 注入、隐私模式、数据脱敏和越权拒绝测试 |
| 审批 | 组织级 Skill、高风险 Skill、外部 MCP/浏览器/CLI/远控 Skill 必须管理员批准 |
| 发布 | 通过 CapabilityRoute 绑定 allowedConsumers 和短期 token；灰度启用，保留上一版本 |
| 回滚 | 风险、误用或质量下降时，可一键禁用或回滚，下一次调用立即失权并写审计 |

智能体“自我进化”的边界：可以提出方案、生成草案、创建测试、运行评测和提交审批；不能在没有评测和人类批准的情况下修改生产 prompt、启用高风险 Skill、绕过权限或读取更多数据。

## 3. 企业组织权限原则

企业组织默认不能把所有 AI 能力开放给所有成员。权限应以“基础可用、强能力可控、高风险可审计”为原则，并吸收 HiClaw 的 Manager / Team Leader / Worker / Human 分层控制面。

| 角色 | 默认能力 | 需要订阅/购买后才能开放 | 仍需额外审批 |
|---|---|---|---|
| 老板 / Owner | 全局看板、风险总览、专业服务转介、账单和组织策略 | 全模型配置、全 Skills/MCP、桌面远控、浏览器自动化、软件/原型开发、组织知识库管理 | 对外提交、批量通知、公开网页采集、生产系统写入 |
| 超级管理员 | 组织配置、成员权限、知识库、模型和工具策略 | 高级 agent、自动化、CLI 工具、MCP 管理、审计查询 | 修改老板权限、导出全量数据、关闭审计 |
| 部门管理员 | 部门知识库、部门模板、部门工作流 | 部门级 Skills、有限浏览器任务、部门报告自动化 | 跨部门数据、财务/税务/法务高风险动作 |
| 普通员工 | 基础问答、组织授权知识库、文档草稿、任务提醒 | 个人效率 Skills、低风险浏览器辅助、个人原型草稿 | 访问敏感知识库、外发文件、远控桌面、执行代码 |
| 外部专业服务方 | 被授权材料包、服务沟通、意见提交 | 平台获客/推广、项目协作空间 | 下载原始材料、跨客户查询、导出企业数据 |

### 3.1 HiClaw 可借鉴的权限控制模式

| HiClaw 模式 | 核心含义 | 安心 AI 转化 |
|---|---|---|
| Manager -> Team Leader -> Worker | 管理者不直接穿透团队内每个 Worker，而是通过 Leader 分派和汇总 | 企业智能体按组织/部门/项目分组；跨团队任务必须经 Leader 或管理员授权 |
| Human permission levels | Human 分为 admin-equivalent、team-scoped、worker-only 等访问层级 | 映射老板/超级管理员、部门管理员、普通员工、外部服务方，明确谁能 @ 哪类 agent、看哪些房间 |
| Declarative channel policy | 使用 allow/deny extra 控制谁能在 group/DM 中提及或访问 agent | 本项目需要 `AgentChannelPolicy`：控制会话、项目、客户、部门和外部服务方的可见范围 |
| Matrix room visibility | 人、Manager、Worker 在同一房间，过程可见且可插手 | 高风险任务必须进入可审计工作室；老板/超级管理员可旁听、暂停、接管、终止 |
| Worker consumer token | Worker 只拿 Gateway consumer token，不持有真实 API key/PAT | 所有 LLM/MCP/第三方系统密钥都放在网关/密钥服务，agent 只拿短期可撤销令牌 |
| allowedConsumers | LLM/MCP route 按 consumer 授权，可秒级撤销 | 能力调用按 agent/user/org/project 绑定 allowedConsumers，禁用工具不需要轮换真实密钥 |
| Shared file store | Worker 边缘 stateless，结果和任务材料进入共享对象存储 | 用对象存储承载任务 spec、材料包、结果、审计 artifact，避免 agent 私存敏感数据 |

权限体系升级建议：从传统 RBAC 升级为 **RBAC + ABAC + Capability Policy + Human-in-the-loop**。核心判定不只看角色，还要看订阅、能力风险、隐私模式、设备可信、数据域、任务目的和当前审批状态。

## 4. 智能体风险分级

| 风险级别 | 示例能力 | 默认策略 |
|---|---|---|
| L0 只读基础 | 问答、总结、解释制度、查看授权知识 | 全员可用，仍记录审计 |
| L1 草稿生成 | 合同/通知/制度/报告草稿、原型草图、代码片段 | 全员可用但必须标记为草稿 |
| L2 内部写入 | 创建任务、写入知识库、生成内部小工具、修改项目文档 | 需部门权限或管理员授权 |
| L3 外部执行 | 浏览器填报、发送邮件/消息、调用外部 MCP、网页采集 | 需订阅 + 管理员审批 + 操作留痕 |
| L4 高风险控制 | 桌面远控、执行代码、批量导出、财务/税务/法务正式提交 | 仅老板/超级管理员或被临时授权人；强制二次确认和审计 |
| L5 禁止或专项审批 | 绕过访问控制、规避验证码/反爬、读取无授权数据、关闭审计 | 默认禁止；如有合法必要，走专项合规审批 |

## 4.1 权限决策因子

每一次智能体动作必须形成可解释授权结果：

| 决策因子 | 示例 |
|---|---|
| subscription | 组织是否购买高级能力、专业服务、远控、浏览器执行、软件工作台 |
| actor_role | 老板、超级管理员、部门管理员、员工、外部服务方 |
| capability | LLM、Skill、MCP、CLI、浏览器、采集器、桌面远控、代码执行 |
| risk_level | L0-L5 |
| data_scope | 个人、部门、组织、客户项目、本地绝密、外部服务材料包 |
| privacy_mode | 本地/绝密、混合、云端 |
| device_trust | 已配对桌面、已信任移动端、未授权设备、外部通道 |
| channel_policy | 谁能在会话/房间中看到、@ 提及、分派或接管 agent |
| approval_state | 无需审批、待审批、已批准、已撤销、已过期 |

拒绝结果必须说明：缺订阅、角色不足、能力未启用、隐私模式禁止、设备不可信、审批缺失、数据越界或风险级别过高。

## 5. 不应直接照搬的部分

- 不把个人助手式“默认完全信任用户”照搬到企业组织。企业场景必须默认最小权限。
- 不引入“绕过反爬/验证码/访问控制”作为卖点。公开数据采集也必须遵守 robots、频控、白名单和法定用途。
- 不让 Skills/MCP/CLI 工具或 Worker agent 直接拿到生产密钥、全量文件或无边界 shell；真实密钥应由网关/密钥服务注入，agent 只持有可撤销 consumer token。
- 不把自动生成软件/原型等同于可上线软件。任何可部署、可联网、可读写企业数据的产物都要测试、安全审查和审批。
- 不把记忆系统做成全员共享黑盒。个人记忆、组织记忆、客户项目记忆必须分层、可删除、可导出、可审计。

## 6. 建议进入 OpenSpec 的新增能力

1. **工作助手模式**：写作、总结、会议、报告、培训、内部制度、任务提醒。
2. **软件/原型工作台**：低代码表单、流程原型、内部小工具、数据脚本、CLI harness、设计原型。
3. **可控浏览器执行器**：网页核验、公开资料采集、政务/税务/工商表单辅助、截图留痕。
4. **多模态知识库**：票据、合同、扫描件、表格、公式、图像、PPT、网页证据统一入库和检索。
5. **能力市场与治理**：模型、Skills、MCP、CLI、浏览器、采集器全部进入 capability registry。
6. **企业智能体治理**：订阅、角色、设备、数据、工具、风险级别、审批、审计、撤销和回滚统一管理。
7. **协作式多智能体控制面**：借鉴 HiClaw，增加 Manager/Leader/Worker/Human 结构、声明式通信策略、房间可见审计、共享任务 artifact 和 Gateway credential isolation。
8. **可信会话体验**：借鉴 Codex/Claude 的过程可见、artifact-first、可打断/可恢复和能力可发现模式。
9. **Skills 进化系统**：建立 Skill 生命周期、评测门禁、审批、灰度、回滚和记忆治理，让智能体能持续变强但不越权。
