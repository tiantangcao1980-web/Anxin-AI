# AI 生成管线性能优化方案

> 基于 Pretext 架构思想和当前系统瓶颈分析，制定分优先级的优化实施方案。

---

## 0、Claude 已推进任务复盘（2026-03-31）

### 已完成且方向正确

1. 完成了对 `pretext` 的定位纠偏：它不是 AI 生成项目，而是“预处理 + 极快热路径”的文本布局引擎。
2. 验证了其“几百倍性能提升”数据在文本重排场景下基本属实，适合借鉴的是架构思想，而不是直接复用代码。
3. 完成了我方 AI 生成链路的瓶颈归因：多 Agent 串行阻塞、三次串行 LLM、无对话历史、配置重复回库等。

### 需要从“分析”切到“可验证落地”的点

1. 先建立稳定回归基线，再推进更大的链路改造；否则 P0/P1 改动会被旧测试和接口契约漂移拖慢。
2. 优先处理“小改动高收益”项：配置缓存、输入无效请求拦截、对话历史透传。
3. 将优化拆成“单点可测”任务，而不是一次性并行改大链路。

### 第一轮已落地（Codex）

1. `LLMService` 新增默认配置 TTL 缓存（60 秒）和失效机制，配置创建/更新/删除/切默认/启停时自动清缓存。
2. `BaseLegalAgent.chat()` 与 `stream_chat()` 改为复用统一的”获取有效 LLM 配置”入口，消除了重复的数据库自愈逻辑。
3. `/api/v1/chat` 输入层新增空消息校验，避免空白消息落入完整的多 Agent/LLM 链路。
4. 单 Agent 流式链路、同步直连 Agent 链路，以及 WebSocket 单 Agent 回复链路已补齐最近对话历史透传。
5. 补充缓存单测、历史透传单测，并修复一组已经落后于当前接口契约的聊天测试。

### 第二轮已落地（Claude Opus）

6. **多 Agent DAG 链路历史透传**：新增 `_task_history_var` contextvars，`_execute_single_task` 和 `execute_with_lifecycle`（含替代 Agent 接管路径）在执行前设置，`chat()` 和 `stream_chat()` 在 `history` 参数为 None 时自动从 contextvars 获取。所有 Agent 的 `process()` 方法无需修改即自动获得对话历史。
7. **合并意图识别+需求分析**：新增 `CoordinatorAgent.analyze_and_classify()` 方法，单次 LLM 调用同时完成意图分类和需求完整度判断。`analyze_task()` 增加 `pre_intent` 预注入机制，已有 intent 时跳过重复识别。复杂消息路径从 3 次串行 LLM 降到 2 次（关键词命中时降到 1 次）。
8. **真流式单 Agent 快速路径**：对 11 种单 Agent 意图（QA_CONSULTATION、DUE_DILIGENCE、DOCUMENT_DRAFTING 等），在 `is_complex` 路径中直接走 `stream_chat` 真流式输出，绕过 `process_task` DAG 编排。首 token 延迟从”等待全部 Agent 完成后伪流式”降到”第一个 token 立即可见”。失败时自动降级回 `process_task`。
9. **动态 max_tokens**：新增 `_estimate_max_tokens()` 根据消息复杂度和意图自动分档（512/2048/4096）。`stream_chat` 新增 `max_tokens` 参数支持。应用于真流式快速路径和单 Agent 流式路径。

### 第三轮已落地（Claude Opus）

10. **Prompt 模板化管理**：创建 `backend/src/prompts/` 模块，包含 `load_prompt()` 加载器（支持文件缓存、自动刷新、变量插值、回退默认值）。迁移 20 个 prompt 到 `.txt` 模板文件（17 个 Agent system prompt + 2 个 Coordinator prompt + 1 个 requirement analysis prompt）。所有 Agent 文件改为 `load_prompt("agents/xxx.txt")` 加载。
11. **WebSocket handler 拆分**：将 `websocket_chat`（1534 行）拆分为 6 个独立 handler 模块 + 1 个共享上下文类：
    - `chat_handlers/context.py` — `WebSocketContext` 封装所有共享状态和辅助方法
    - `chat_handlers/a2ui_handler.py` — A2UI 前端交互事件
    - `chat_handlers/workspace_handler.py` — 工作台确认/动作
    - `chat_handlers/canvas_handler.py` — Canvas 编辑/AI优化
    - `chat_handlers/due_diligence_handler.py` — 企业尽调强路由
    - `chat_handlers/rag_handler.py` — 知识库 RAG 研究模式
    - 重构后 `websocket_chat` 降到 1040 行（减少 ~500 行），各 handler 可独立测试

## 一、当前架构问题总览

### 请求处理流水线（WebSocket 路径）

```
用户消息 → A2UI事件 → 隐私检查 → 尽调强路由 → RAG路由
         → 意图检测 → 简单/复杂判断 → [需求分析LLM]
         → [Coordinator意图LLM] → [Agent执行LLM] → 伪流式推送
```

### 已识别瓶颈

| 编号 | 瓶颈 | 影响 | 严重度 |
|------|------|------|--------|
| B1 | 多 Agent 串行阻塞，完成后才伪流式推送 | 首 token 延迟极高（数十秒） | **P0** |
| B2 | 复杂消息 3 次串行 LLM 调用（需求分析→意图→执行） | 响应延迟叠加 | **P0** |
| B3 | LLM 配置每请求查数据库 | 不必要 I/O 延迟 | **P0** |
| B4 | 流式 Agent 不传对话历史 | 多轮对话质量差 | **P0** |
| B5 | 无动态 max_tokens 控制 | 简单问题冗长回复 | **P1** |
| B6 | Prompt 硬编码在代码中 | 无法快速迭代/A/B测试 | **P1** |
| B7 | WebSocket handler 500+ 行 | 难维护/测试 | **P2** |
| B8 | 尽调/RAG/隐私逻辑三重重复 | 修改一处需同步三处 | **P2** |

## 二、P0 优化：速度提升（直接影响用户感知）

### 2.1 LLM Config 内存缓存

**问题**：`BaseLegalAgent._load_llm_config()` 每次 WebSocket 消息都查数据库。

**方案**：添加带 TTL 的服务层缓存，配置变更频率极低（分钟级），缓存 60 秒即可。

```python
# backend/src/services/llm_service.py
class LLMService:
    async def get_cached_effective_config(config_type="llm"):
        # 1. 读 TTL 缓存
        # 2. miss 时从数据库加载默认配置，回退最近启用配置
        # 3. create/update/delete/set_default/toggle_active 时主动失效
        ...
```

**当前状态**：已落地。

**收益**：每次请求减少 1 次数据库查询（~5-20ms），并统一了 `chat/stream_chat` 的配置恢复逻辑。

### 2.2 合并意图识别 + 需求分析

**问题**：复杂消息走两次串行 LLM：需求分析 → 意图识别。

**方案**：合并为单次调用，一个 prompt 同时输出需求完整性判断和意图分类。

```
当前：需求分析(LLM, ~2s) → 意图识别(LLM, ~2s) → Agent执行(LLM)  = 首token ~6s+
优化：合并意图+需求(LLM, ~2s) → Agent执行(LLM)  = 首token ~4s+
进一步：关键词命中时(0ms) → 直接Agent执行  = 首token ~2s
```

**关键词快速路径覆盖率目标**：从当前 ~80% 提升到 ~90%（扩充法律领域关键词）。

### 2.3 真流式多 Agent 输出

**问题**：多 Agent DAG 执行完毕后，才将完整结果文本按 20ms 间隔分块推送（伪流式）。

**方案**：
1. DAG 中第一个 Agent 使用真流式（`stream_chat`），token-by-token 推送
2. 后续 Agent 结果以增量方式追加
3. 保留 `_stream_response_tokens` 仅作为非流式 Agent 的回退

```python
# 伪代码
async def execute_dag_streaming(agents, message, ws):
    first_agent = agents[0]
    # 第一个 Agent 立即流式输出
    async for token in first_agent.stream_chat(message):
        await ws.send_json({"type": "content_token", "content": token})

    # 后续 Agent 增量追加
    for agent in agents[1:]:
        result = await agent.chat(message, context=first_result)
        await ws.send_json({"type": "agent_result", "content": result})
```

**收益**：用户首 token 感知从"等待所有 Agent 完成"变为"第一个 Agent 开始输出即可见"。

### 2.4 WebSocket 路径补对话历史

**问题**：`stream_chat()` 只发送 system + 当前 user 消息，完全无多轮上下文。

**方案**：在 WebSocket handler 中，调用 Agent 前取最近 N 条对话历史，传入 messages 列表。

```python
# 在 websocket_chat 中，调用 Agent 前
recent_history = await chat_service.get_recent_messages(
    conversation_id=conversation_id,
    limit=10  # 最近 10 条
)
history_messages = [
    {"role": msg.role, "content": msg.content}
    for msg in recent_history
]

# 传入 Agent
result = await agent.chat(
    message=user_message,
    history=history_messages  # 新增参数
)
```

**收益**：多轮对话质量从"无上下文"提升到"有 10 轮上下文"。

**当前状态**：已完成单 Agent 真流式、同步直连 Agent、WebSocket 单 Agent 回复三条链路；复杂多 Agent DAG 仍待继续补齐。

### 2.5 输入层空消息拦截

**问题**：空消息此前会进入完整聊天链路，触发多 Agent、MCP 初始化、外部连接重试，既慢又浪费资源。

**方案**：在 `ChatMessage` 模型层校验 `content.strip()`，对空消息直接返回 `422`。

**当前状态**：已落地。

**收益**：
- 减少一次无意义的 LLM/Agent 处理链
- 避免空消息场景下的 30s+ 超时与外部依赖噪声
- 让前端更容易给出即时表单反馈

## 三、P1 优化：质量提升

### 3.1 动态 max_tokens

**方案**：根据问题复杂度分档控制输出长度。

| 复杂度 | 判断条件 | max_tokens |
|--------|---------|------------|
| 简单 | 招呼语、是否类问题、<20字 | 256 |
| 中等 | 单一法律问题、概念解释 | 1024 |
| 复杂 | 多步骤分析、文书起草 | 4096 |
| 工作台 | 尽调报告、合同审查 | 8192 |

### 3.2 Prompt 模板化管理

**方案**：将散落在代码中的 prompt 统一到配置目录。

```
backend/src/prompts/
├── coordinator/
│   ├── intent_classification.txt
│   └── task_planning.txt
├── agents/
│   ├── contract_review.txt
│   ├── legal_consultation.txt
│   └── document_drafting.txt
└── system/
    ├── requirement_analysis.txt
    └── response_formatting.txt
```

支持：
- 版本管理（Git 追踪）
- 热更新（文件变更自动重载，无需重启）
- 变量插值（`{user_preference}`、`{conversation_context}`）

## 四、P2 优化：架构改善

### 4.1 拆分 WebSocket Handler

**当前**：`websocket_chat` 约 500 行，包含所有路由逻辑。

**方案**：策略模式拆分。

```python
# backend/src/api/routes/chat_handlers/
├── __init__.py          # ChatRouter 策略分发
├── a2ui_handler.py      # A2UI 事件处理
├── workspace_handler.py # 工作台交互
├── canvas_handler.py    # Canvas 编辑
├── privacy_handler.py   # 隐私检查 + PII 脱敏
├── due_diligence.py     # 尽调强路由
├── rag_handler.py       # 知识库 RAG
└── chat_handler.py      # 通用对话（意图→Agent→流式）
```

### 4.2 统一 Service 层

**当前**：尽调/RAG/隐私还原在 `chat_service.py`（同步+流式）和 `chat.py`（WebSocket）三重实现。

**方案**：统一到 Service 层，三个入口复用同一实现。

```python
class ChatOrchestrator:
    """统一编排层，被 HTTP/流式/WebSocket 三个入口共享"""

    async def process(self, message, context) -> ChatResult:
        # 1. 隐私检查
        message = await self.privacy_service.check(message, context)
        # 2. 路由决策
        route = await self.router.decide(message, context)
        # 3. 执行
        result = await route.handler.execute(message, context)
        # 4. 后处理
        return await self.postprocess(result, context)
```
