### 0.5 2026-05-08 产品定位补充：中小企业经营风险 AI 平台

本轮补充把项目的目标客户、服务供给方和商业价值链进一步明确。安心 AI 法务不应只被理解为“AI 法务工具”，而是面向中小企业日常经营的 **法务、财务、税务、合规、舆情风险处理平台**，并在重大事项上连接可信赖的专业服务人员。

| 角色 | 主要用户 | 核心诉求 | 平台责任 |
|---|---|---|---|
| 企业需求方 | 中小企业老板、股东、高管、行政、人事、财务、法务/合规兼岗人员 | 低成本处理日常合同、劳动人事、回款、税务、工商、供应商/客户尽调、舆情风险和内部办公问题 | 用 AI 完成初筛、解释、文书草拟、流程提醒和风险分级；明确提示“不构成最终专业意见” |
| 专业服务方 | 律师、律所、税务师、税务师事务所、财务顾问、会计/审计人员及机构 | 获取可信线索、提升服务转化、降低重复沟通成本、维护客户关系 | 做资质认证、利益冲突检查、服务目录、SLA、评价、线索归因和结算 |
| 平台运营方 | 平台管理员、审核/风控/客服人员 | 保障供需匹配质量、控制合规风险、提升商业转化 | 做审核、风控、证据链、投诉处理、数据脱敏、营销活动和获客分析 |

新增产品原则：

1. **AI 处理日常，专业人员处理重大事项**：普通咨询、文书草拟、政策解释、风险提示优先由 AI 完成；当事项涉及高金额合同、劳动争议、税务稽查、行政处罚、诉讼仲裁、重大舆情、股权融资、并购重组等高风险场景时，系统必须给出“建议转专业人士”的明确动作。
2. **服务供给方从律师扩展到专业服务网络**：现有“律师协助通道”继续保留，但规范上升级为“专业协助通道”，服务类型至少预留 legal / tax / accounting / finance / compliance 五类；当前实现仍以律师/律所为主，税务师、税务事务所、财务人员属于后续扩展和验收项。
3. **舆情监测是企业风险入口**：舆情监测不仅是资讯展示，而是客户风险预警、合规处置、危机公关和专业服务转介入口。监测对象、告警级别、处置建议、转人工服务都必须可追踪。
4. **推广获客是服务端商业价值**：未来推广获客功能应服务于律师、律所、税务师事务所、财务顾问等服务方，但必须以用户授权、线索来源可追踪、广告/推荐标识清晰、隐私脱敏和反骚扰为前提。
5. **双边平台指标分开看**：企业侧关注风险处理成功率、响应时效、转人工满意度、重大风险拦截率；服务侧关注线索质量、响应 SLA、转化率、复购率、投诉率和利益冲突拦截率。

对后续架构的直接影响：

- **用户模型 / RBAC**：`needer/provider` 之外，需要服务方 `provider_type`、资质类型、执业/机构认证状态、服务范围、可接单区域和利益冲突约束。
- **A2UI / Chat 工作台**：高风险识别后应统一输出“转专业人士”卡片，卡片必须绑定具体服务类型、风险摘要、材料包和授权状态。
- **任务 08b**：从“律师市场”扩展为“专业服务市场”，但当前 P0 仍先把律师/律所路径做实；税务/财务供给方作为 P1/P2 进入规范和接口预留。
- **任务 09**：舆情监测从风险提示升级为商业化入口之一，需要告警、处置建议、人工服务转接和后续效果追踪。
- **任务 10**：订阅与按次付费需要区分企业侧 AI 套餐、专业服务按次/项目计费、服务方获客/推广产品。

### 0.6 2026-05-08 产品定位补充：全设备智能助手与本地优先扩展平台

在中小企业经营风险 AI 平台之上，本项目的长期定位进一步升级为 **全面的智能助手平台**。安心 AI 不只是一个 Web 法务应用，而应成为用户在桌面端、移动端和小程序中都能安装、登录、配置和持续使用的智能工作入口；其中桌面客户端是主要生产力工作站，移动端是随身助手和远程控制入口。

| 能力层 | 产品要求 | 工程影响 |
|---|---|---|
| 桌面主工作站 | 可安装、可离线、可拖拽文件、可本地处理敏感任务，承载日常办公中的法务、财务、税务、舆情和资料分析 | 桌面端必须拥有本地加密库、本地模型调用、本地知识库索引、任务队列、Skills/MCP 配置入口和可审计执行日志 |
| 移动随身助手 | 具备桌面端的核心咨询、审批、通知、文档查看和风险提醒能力 | 移动端不能只做消息壳；必须能读取跨设备会话、审批高风险动作、查看材料包和处理轻量任务 |
| 移动远程控制桌面 | 用户可在移动端远程唤起、查看和控制已配对桌面客户端执行任务 | 需要设备配对、权限确认、命令队列、执行状态回传、取消/撤销、敏感动作二次确认和审计日志 |
| 任意大模型配置 | 用户或组织可配置云端模型、本地模型、自托管模型和第三方兼容 endpoint | LLM 配置必须支持 provider/endpoint/model/key/mode/org scope，切换模型不得绕过隐私模式和订阅守卫 |
| Skills 与 MCP 扩展 | 用户可安装或启用不同技能、工具连接器和 MCP Server | 需要 capability registry、权限分级、工具调用日志、失败回滚、组织级禁用清单和最小授权 |
| 独立知识库 | 个人、组织、项目、客户和本地知识库可独立管理 | 知识库必须有来源、引用、权限、脱敏、版本、离线缓存和本地向量索引策略 |
| 本地模型绝对安全 | 绝密/本地模式下，可使用本地模型与本地知识库完成任务，数据默认不离开设备 | 本地模式必须 fail-closed；任何云端调用、同步、远控上传或外部 MCP 调用都必须显式授权并可审计 |

新增产品原则：

1. **桌面优先，移动协同**：桌面客户端负责重型文件、知识库、本地模型和长任务；移动端负责随身访问、审批确认、远程控制和跨设备继续工作。
2. **用户可配置，不锁死模型与工具**：平台默认提供稳定模型和官方 Skills/MCP，但企业用户必须能够接入自有模型、自有工具、自有知识库和本地安全设备。
3. **本地优先不是离线弱化版**：本地模式应是高安全等级模式，覆盖合同、文档、问答、知识库、审计记录和本地任务队列；不能把本地模式做成仅 UI 可选项。
4. **远程控制必须可解释、可撤销、可审计**：移动端对桌面的远程控制不能静默执行高风险操作；所有命令都要有发起人、设备、时间、权限、状态和结果。
5. **扩展能力必须有边界**：任意 LLM、Skills、MCP 带来商业价值，也带来数据外流和工具越权风险；因此要有组织级策略、权限最小化、调用日志和安全审查门禁。

对后续架构的直接影响：

- **桌面端任务 11a**：从“窗口外观 + 快速问答 + 拖拽分析”升级为桌面主工作站 MVP，需要暴露本地模型、知识库、Skills/MCP 和隐私模式状态入口。
- **同步任务 11b**：从数据同步扩展为跨设备会话、移动远控命令、审批确认和执行状态回传的基础协议。
- **移动任务 11c**：从移动 Beta 升级为“移动助手 + 桌面远控端”，必须补设备配对、远程命令、状态回传、撤销和真机验收。
- **任务 02 / 07 / 03**：LLM 配置、知识库、Agent/Skills/MCP 调用需要统一到同一套 capability registry 和隐私模式守卫。
- **OpenSpec**：商业交付规范必须把“桌面主工作站、移动远控、本地模型、本地知识库、任意模型/Skills/MCP 配置”列为验收门槛。

### 0.7 2026-05-08 参考项目补充：Agentic Workspace 与企业智能体治理

本轮参考了 Hermes Agent、OpenClaw、HiClaw、DeepTutor、CLI-Anything、RAG-Anything、browser-use、Scrapling 等项目，形成 `docs/references/agentic-platform-benchmark-2026-05-08.md`。这些项目共同说明：用户未来需要的不只是问答助手，而是能持续学习、能接工具、能操作软件、能处理多模态资料、能跑浏览器和自动化任务的综合智能体工作台。

可吸收能力：

1. **自改进 Skills 与记忆**：借鉴 Hermes 的学习闭环和 Skills 生命周期，但在企业场景中必须增加审批、版本、回滚和组织级禁用。
2. **本地网关与设备配对**：借鉴 OpenClaw 的本地 Gateway、DM pairing、节点和沙盒思路，用于桌面主工作站、移动远控和消息入口。
3. **协作式多智能体控制面**：借鉴 HiClaw 的 Manager/Team Leader/Worker/Human、声明式通信策略、房间可见审计、Gateway consumer token 和真实密钥隔离，用于企业智能体权限管控。
4. **统一工作区与个性化助手**：借鉴 DeepTutor 的多模式同线程、Knowledge Hub、Co-Writer、TutorBot 和多用户隔离，把企业培训、制度问答、报告写作和知识运营纳入安心 AI。
5. **软件/原型开发工作台**：借鉴 CLI-Anything 的 agent-native CLI 生成和测试文档流水线，让用户能生成内部小工具、流程原型、数据脚本和设计原型。
6. **多模态 RAG**：借鉴 RAG-Anything 的 PDF/Office/图片/表格/公式/图谱/混合检索能力，升级合同、票据、财报、税表、PPT、扫描件和网页证据处理。
7. **可控浏览器执行器**：借鉴 browser-use 的浏览器 agent 和 CLI，把网页核验、填表草稿、资料下载、截图留痕变成受控能力。
8. **合规公开数据采集**：借鉴 Scrapling 的 spider、robots、频控、开发缓存和 MCP 数据抽取能力，但不得把绕过访问控制、验证码或反爬作为产品能力。
9. **可信 AI 工作台交互**：借鉴 Codex/Claude 的公开体验原则，长任务要展示计划、步骤、工具状态、失败原因、引用证据、可编辑 artifact、暂停/恢复/接管和跨设备继续入口。
10. **Skills 与智能体自我进化**：Skill 可以基于失败案例和用户反馈持续升级，agent 可以生成改进提案、测试和评测结果，但不能无评测、无审批自改生产能力。

企业智能体治理原则：

- 企业组织默认开放基础能力：问答、总结、授权知识库、文档草稿、任务提醒。
- 只有已订阅或购买服务的组织，且由老板/Owner 或超级管理员开启，才能获得完整能力：任意模型、Skills/MCP、浏览器执行、桌面远控、自动化、软件/原型工作台、CLI harness。
- 普通员工、部门管理员、外部专业服务方都必须按角色、数据范围、能力等级和审批流划边界。
- 每次能力调用都必须经过 `subscription + role + permission + risk_level + privacy_mode + device_trust` 校验。
- 多智能体协作必须有 AgentManager、AgentTeam、AgentWorker、HumanParticipant、ChannelPolicy、CapabilityRoute 和 SharedArtifactStore 等可审计控制面对象。
- Worker/Agent 不得直接持有真实密钥；LLM、MCP、财税接口、GitHub PAT、浏览器账号等凭据必须由网关/密钥服务托管，Agent 只拿短期可撤销 consumer token。
- L3/L4 高风险能力必须有二次确认、审计日志、撤销/回滚；L5 能力默认禁止，专项审批后才能进入合规评估。
- Skills 进化必须有 owner、版本、风险级别、评测集、审批状态、灰度、回滚和审计；已回滚或未批准 Skill 的下一次调用必须失败。
- 交互体验必须把“过程透明、证据可追溯、结果可编辑、用户可掌控”作为核心验收，而不是只验收 API 返回成功。

对后续架构的直接影响：

- **新增 TASK-12**：企业智能体工作台与治理引擎，覆盖通用工作助手、软件/原型工作台、浏览器执行器、CLI harness、自动化、权限治理、多智能体控制面和 Skill Evolution Gate。
- **任务 03 / 04**：Agent/A2UI 不再只服务法务流程，也要支持通用工作模式、长任务时间线、工具执行卡、审批卡、沙盒执行卡、artifact 预览和 Skill 进化提案。
- **任务 07**：知识库升级为多模态知识底座，支持票据、财报、税表、扫描件、PPT 和网页证据。
- **任务 11a / 11c**：桌面和移动端需要提供“能力中心”和“执行审计”，让用户看得见当前 agent 能做什么、正在做什么、被谁授权，并可暂停、恢复、取消、接管和跨设备继续。

### 1.4 差异化定位

安心AI法务不是通用办公平台，而是 **垂直法务 AI 智能工作台**。与三大平台的差异：

1. **AI 原生**：AI 不是辅助功能，而是核心工作流驱动引擎
2. **法务专精**：深度理解法律文书、合同条款、判例引用
3. **本地优先**：敏感法律文件优先本地存储，按需同步
4. **混合部署**：支持公有云 SaaS + 私有化部署 + 离线使用

### 4.3 同步协议设计

```
+-----------------------------------------------------------------------+
|                    同步协议 (Sync Protocol)                              |
+-----------------------------------------------------------------------+
|                                                                       |
|  客户端                              服务端                             |
|  +----------------------+           +----------------------+          |
|  | Change Log           |           | Change Log           |          |
|  | (本地操作日志)        |           | (服务端操作日志)       |          |
|  | +------------------+ |           | +------------------+ |          |
|  | | id: uuid         | |           | | id: uuid         | |          |
|  | | entity_type      | |    Push   | | entity_type      | |          |
|  | | entity_id        | | --------> | | entity_id        | |          |
|  | | operation: C/U/D | |           | | operation: C/U/D | |          |
|  | | payload (diff)   | |    Pull   | | payload (diff)   | |          |
|  | | timestamp (HLC)  | | <-------- | | timestamp (HLC)  | |          |
|  | | client_id        | |           | | client_id        | |          |
|  | | sync_state       | |           | | sync_state       | |          |
|  | +------------------+ |           | +------------------+ |          |
|  +----------------------+           +----------------------+          |
|                                                                       |
|  同步流程:                                                             |
|                                                                       |
|  1. 离线操作 -> 写入本地 Change Log (pending 状态)                      |
|  2. 网络恢复 -> 推送 pending changes 到服务端                           |
|  3. 服务端校验 -> 冲突检测                                              |
|  4. 无冲突 -> 写入服务端 -> 广播给其他客户端                             |
|  5. 有冲突 -> 冲突解决策略:                                             |
|     a. 配置类数据: Last-Write-Wins (LWW)                               |
|     b. 合同文档: 版本分叉 + 人工合并                                    |
|     c. 协作编辑: CRDT (Yjs) 自动合并                                    |
|  6. 确认同步完成 -> 更新 sync_state 为 synced                           |
|                                                                       |
+-----------------------------------------------------------------------+
```

**协作编辑方案（CRDT vs OT）**：

采用 **CRDT (Yjs)** 方案，理由：
- 天然支持离线编辑后合并，与 Local-First 理念一致
- 不需要中心化排序服务器（OT 需要）
- 飞书文档已验证 CRDT 在大规模场景的可行性
- Yjs 生态成熟，已有 y-indexeddb（Web）、y-sqlite（桌面）持久化方案

```
|  - 顺序签署: A -> B -> C (上一方签完下一方才收到)                       |
|  - 并行签署: A, B, C 同时收到, 各自独立签署                             |
|  - 混合模式: 先 A 签, 然后 B 和 C 并行签                               |
|                                                                       |
|  催办机制:                                                             |
|  - 自动催办: 超过设定时间未签署, 自动发送提醒                            |
|  - 手动催办: 发起方可随时催办                                           |
|  - 超时处理: 可配置超时自动取消或延期                                    |
|                                                                       |
+-----------------------------------------------------------------------+
```

### 6.3 对接方案

| 服务商 | 定位 | 集成方式 | 优势 |
|-------|------|---------|------|
| e签宝 | 一站式电子签 | REST API | 市场份额大, 法院认可度高 |
| 法大大 | 法律科技专业 | REST API | 法律行业深耕, 存证能力强 |
| 上上签 | 企业级电子签 | REST API | 大企业客户多, 稳定性好 |
| 自建签署 | 长期方案 | CA 对接 | 完全自主可控, 成本可控 |

**推荐路径**: 第一阶段对接 e签宝/法大大 API 快速上线, 第二阶段逐步建设自主签署能力。
