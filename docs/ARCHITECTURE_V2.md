# 安心法务 V2 架构升级规划

**版本**：v2.0
**制定日期**：2026-04-16
**状态**：规划中，分阶段实施
**负责人**：全栈团队

---

## 一、升级目标总览

本次升级是产品架构层面的**三大根本性变革**：

1. **双客户端分离** — 需求方(C端)与服务方(B端律师/律所)独立注册登录，独立品牌，独立体验
2. **三态运行模式** — 本地/混合/云端三种模式，各自独立的数据边界与功能边界
3. **订阅商业化** — 非本地模式需订阅，建立可持续商业模型

## 二、双客户端架构（需求方 vs 服务方）

### 2.1 分离原因

| 维度 | 需求方客户端 | 服务方客户端 |
|------|-------------|-------------|
| **目标用户** | 个人用户、中小企业、HR、企业法务 | 执业律师、律所、法务咨询机构 |
| **核心诉求** | 解决法律问题，降低法务成本 | 获客、提效、管理案源 |
| **付费模式** | 订阅制 + 按次咨询 | 抽佣 + 会员费 + SaaS 订阅 |
| **品牌感知** | 友好亲和、通俗易懂、像 "AI 律师" | 专业严肃、效率工具、像 "律师大脑" |
| **交互设计** | 引导式、苏格拉底追问、可视化 | 高密度信息、快捷操作、看板式 |
| **安全合规** | 隐私保护、数据最小化 | 案源保密、执业合规、利益冲突检查 |

**结论**：必须分离，否则产品定位模糊，两端用户体验都做不好。

### 2.2 分离方案：**同一账号体系，独立客户端入口**

**决策**：不分离用户表，但分离登录入口、注册流程、主应用界面。

```
          ┌────────────── users 表（统一）──────────────┐
          │ user_type: individual | enterprise |       │
          │            platform_lawyer | institution   │
          │ primary_client: needer | provider          │  ← 新增
          └──────────────────────────────────────────────┘
                    ↑                           ↑
                    │                           │
       ┌────────────┴──────────┐     ┌─────────┴──────────┐
       │  需求方客户端          │     │  服务方客户端       │
       │  app.anxinfawu.com    │     │  pro.anxinfawu.com │
       │  /login                │     │  /pro/login        │
       │  /register?type=xxx    │     │  /pro/register     │
       │                        │     │                     │
       │  主入口: /chat         │     │  主入口: /dashboard │
       │  模块: 对话/案件/找律师 │     │  模块: 案源/客户/账单│
       └────────────────────────┘     └─────────────────────┘
```

**技术实现**：
- 前端：单一 React 代码库，通过路由前缀 `/app/*` 与 `/pro/*` 切分界面
- 后端：同一 API，但通过 `primary_client` 字段做权限与功能边界控制
- 部署：未来可选择部署为两个独立域名（`app.xxx` vs `pro.xxx`）或同域分路径
- 移动端：Tauri 桌面版和移动端 App 同样分双端

### 2.3 用户类型到客户端的映射

| user_type | primary_client | 默认主入口 | 可访问的另一端？ |
|-----------|----------------|------------|------------------|
| `individual` | needer | /app/chat | 否 |
| `enterprise` | needer | /app/workspace | 否 |
| `platform_lawyer` | provider | /pro/dashboard | 以"服务者身份"查看需求市场 |
| `institution` | provider | /pro/firm | 以"服务者身份"查看需求市场 |

**关键决策**：
- 一个自然人可能**同时**是个人用户和兼职律师 — 允许同账号切换客户端（类似淘宝/千牛）
- 后台管理(`/admin`)独立于两端，仅超管和 org_admin 可访问

### 2.4 注册流程分流

**/login（需求方）**
- 默认注册为个人用户
- 提供"我是企业用户"切换卡片（填企业名、统一社会信用代码等）
- 不出现"我是律师"选项 — 律师必须去服务方端

**/pro/login（服务方）**
- 默认注册为个人律师（需上传执业证）
- 提供"我是律所管理员"切换卡片（填律所名、营业执照）
- 不出现"我是个人用户"选项

**跨端提示**：
- 在 /login 页面底部放"您是律师？去服务方端注册 →" 链接
- 反之亦然

## 三、三态运行模式

### 3.1 模式定义

| 模式 | 数据边界 | AI 来源 | 网络要求 | 适用场景 |
|------|---------|---------|---------|---------|
| **本地 (LOCAL)** | 数据不出设备 | 用户自配本地大模型(Ollama/LMStudio) | 不需要 | 高保密律所、涉密案件、离线办公 |
| **混合 (HYBRID)** | 敏感数据本地处理，非敏感上云 | 本地模型 + 云端模型 | 需要 | 平衡隐私与性能的常规用户 |
| **云端 (CLOUD)** | 全量上云 | 云端模型 | 需要 | 追求最佳体验的个人/轻度企业 |

### 3.2 功能可用性矩阵

下面是**关键功能在各模式下的可用性**（✅ 可用 / ⚠️ 降级 / ❌ 禁用）：

| 功能 | 本地 | 混合 | 云端 | 说明 |
|------|:----:|:----:|:----:|------|
| 智能对话（基础） | ✅ | ✅ | ✅ | 本地需配置LLM，否则不可用 |
| 合同审查 | ✅ | ✅ | ✅ | 本地模式用本地LLM审查 |
| 文书起草 | ✅ | ✅ | ✅ | 同上 |
| 需求发掘/苏格拉底追问 | ✅ | ✅ | ✅ | 纯规则 + 本地LLM补强 |
| **舆情监测** | ❌ | ✅ | ✅ | 需要爬虫+云端NLP，本地无法实现 |
| **法律智库（法规/案例）** | ⚠️ | ✅ | ✅ | 本地需先在联网模式下载数据包 |
| **通用模板市场** | ⚠️ | ✅ | ✅ | 本地需先下载模板包 |
| 案件管理 | ✅ | ✅ | ✅ | 本地纯CRUD，不需联网 |
| 合同管理 | ✅ | ✅ | ✅ | 同上 |
| **找律师** | ❌ | ✅ | ✅ | 本地无法访问律师数据库 |
| **IM即时通讯** | ❌ | ✅ | ✅ | 需要WebSocket云端转发 |
| **知识图谱** | ⚠️ | ✅ | ✅ | 本地需下载图谱数据包 |
| **尽职调查** | ❌ | ✅ | ✅ | 需要爬工商/诉讼API |
| AI 模型能力 | 受本地LLM限制 | 可在敏感任务用本地 | 最佳 | — |

### 3.3 模式切换用户体验

**切换流程**：
1. 设置页提供三态切换开关
2. 从本地切到混合/云端：需要已有订阅；如无订阅，弹出订阅引导
3. 从云端切到本地：提示"以下云端数据需要同步到本地：[列表]"，用户确认后同步
4. 不允许静默切换 — 每次切换都需明确确认

**离线提示**：
- 本地模式下点击不可用功能时，统一组件 `<ModeGate>` 弹框：
  > "舆情监测需要云端服务支持。请切换到混合模式或云端模式使用。"
  > [了解订阅] [切换到混合模式] [取消]

### 3.4 资源下载机制（本地模式的"离线包"）

**法律智库**：约 33,102 条文书 + 法规数据
- 完整包约 2GB，提供分包下载（民事/商事/劳动/刑事...）
- 本地 SQLite + FTS5 索引
- 版本号机制，支持增量更新

**通用模板市场**：
- 按场景分类下载（合同/文书/公司章程...）
- 每个模板包 < 10MB

**下载流程**：
- 在混合/云端模式下，设置页 → "离线资源管理" → 勾选需要下载的模块 → 后台下载
- 下载完成后，即使切到本地模式也能使用
- 本地模式下若未下载则显示"请先在云端模式下载"

## 四、订阅商业化体系

### 4.1 订阅分层

| 方案 | 价格建议 | 模式 | 核心权益 | 目标群体 |
|------|---------|------|---------|---------|
| **Free** | ¥0 | 仅本地 | 需要自配LLM，所有本地功能 | 技术爱好者、高保密律所 |
| **Lite** | ¥29/月 | 混合 | 云端基础模型调用10万token/月 | 个人轻度用户 |
| **Pro** | ¥99/月 | 云端 | 云端高级模型、舆情、找律师全开放 | 个人深度用户、小微企业 |
| **Team** | ¥499/月起 | 云端 | 5 席位起，企业协同、审批流 | 中小企业法务 |
| **Enterprise** | 面议 | 混合/云端/私有 | 私有部署、定制模型、专属客服 | 大型企业、律所 |
| **Lawyer Pro** | ¥199/月 | 云端 | 律师专属功能全开放、案源推送 | 执业律师 |
| **Firm Pro** | ¥999/月起 | 云端 | 律所管理、多律师协作 | 律所 |

### 4.2 订阅 → 功能的映射机制

在 `subscriptions` 表中存储：
```
user_id | plan_id | status | starts_at | expires_at | features (JSON)
```

`features` 字段存细粒度权限，例如：
```json
{
  "modes": ["local", "hybrid", "cloud"],
  "sentiment_monitoring": true,
  "legal_knowledge_base": true,
  "template_marketplace": true,
  "ai_quota_tokens": 100000,
  "ai_quota_reset": "monthly",
  "lawyer_matching": true,
  "team_seats": 5
}
```

运行时检查：`SubscriptionService.can_access(user_id, feature_key)` → bool

### 4.3 支付集成

- 微信支付 + 支付宝（已有集成）
- 订阅管理页：查看当前订阅、账单历史、取消/升级
- 到期前 7 天邮件/短信提醒

## 五、**你可能忽略但一定会需要的细节**（主动补充）

### 5.1 跨设备数据同步

**场景**：用户在 PC 用云端模式建了案件，回家用手机看时发现找不到。

**方案**：
- 所有业务数据默认云端同步（订阅用户）
- 本地模式下的数据留本地，切到云端时提示"是否上传历史本地数据？"
- 提供"合并/覆盖/不上传"三选项

### 5.2 跨模式数据迁移

**场景**：用户一直用云端，某天切到本地，云端数据怎么办？

**方案**：
- 切换前弹出选项：
  - "在本地保留最近 30 天数据的副本"（推荐）
  - "全量导出到本地"
  - "切换后仅保留本地新建数据"
- 一次性下载，之后本地新增不会再同步到云端（保持本地隔离）

### 5.3 账号多端一致性

**场景**：同一律师账号，在手机装了服务方 App，在电脑开了需求方网页版，如何一致？

**方案**：
- JWT 刷新机制不变
- 客户端偏好 `primary_client` 存在 User 表，但允许在 URL 中临时切换（`?as=needer`）
- 数据根据 `primary_client` 默认视图呈现

### 5.4 订阅与客户端的映射

**问题**：一个自然人同时是需求方用户和兼职律师，订阅会不会乱？

**方案**：
- **一个账号两份订阅**：需求方订阅（Lite/Pro）+ 服务方订阅（Lawyer Pro）
- 在账单中心分别显示
- 不互相代替 — Lawyer Pro 不自动包含 Pro

### 5.5 本地模式下的"试用体验"

**问题**：新用户纯本地模式，什么都用不了（没 LLM 配置），体验会差到直接流失。

**方案**：
- 新用户首次打开默认进入"**体验云端模式（3天免费）**"
- 3 天后提示订阅；如不订阅，自动降到本地 Free
- 本地 Free 提供 "使用本地 LLM 快速配置向导"（10分钟搞定 Ollama）

### 5.6 利益冲突检查（律师端专属）

**问题**：律师接了甲方的案子，不能再接乙方起诉甲方的案子。

**方案**：
- 服务方端接单前，系统自动扫描历史案件的当事人
- 发现潜在冲突时弹出警告
- 对律所端必需；个人律师端可选

### 5.7 案源市场（双端的连接点）

**场景**：需求方发布需求 → 系统匹配 → 服务方看到机会 → 接单/投标。

**方案**：
- 需求方：案件详情页勾选"允许向律师推送"（默认关闭）
- 服务方：有独立的"案源市场"页，按专业领域/地域筛选
- 双方互评机制：需求方评律师，律师评客户
- 这是平台商业模式的核心，必须做

### 5.8 数据主权声明（本地模式的卖点）

**问题**：律所最敏感的是数据，必须给他们"数据绝对不出本地"的承诺。

**方案**：
- 本地模式下，**系统禁用所有出站网络请求**（通过 Tauri 策略）
- 提供可审计的日志，证明没有数据外泄
- 这是律所端的**核心卖点**，必须做得明明白白

### 5.9 模型可插拔（不绑定腾讯/OpenAI）

**问题**：云端默认用混元/DeepSeek，但企业客户可能要求用自己的 OpenAI/Azure。

**方案**：
- Enterprise 方案支持自定义 LLM 端点
- 配置在 `LLMConfig` 表已有，只需打开前端配置入口

### 5.10 合规审计日志

**问题**：律所端必须有完整的操作审计（为谁做了什么、何时做的、数据动向）。

**方案**：
- 服务方端强制开启完整审计日志
- 可导出 PDF 作为律所合规证明
- 本地模式日志只在本地；云端模式日志同步

### 5.11 律所内部分级（服务方端独有）

**问题**：律所里有合伙人、授薪律师、实习律师、律师助理，权限不同。

**方案**：
- 服务方端 org_admin 可配置内部角色（已有部分基础设施）
- 不同角色看到的客户/案件范围不同
- 合伙人可见全部，授薪律师只看自己负责的

### 5.12 版本升级的向后兼容

**问题**：老用户升级到 V2 后，数据怎么办？

**方案**：
- User 表新增 `primary_client` 字段，默认值按 `user_type` 推断
- 老用户首次登录 V2，弹引导："欢迎来到 V2，我们注意到您是律师，为您切换到服务方端 →"
- 数据结构不变，只是路由和 UI 变化
