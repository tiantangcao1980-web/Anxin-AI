# Chat 输入编排栏与模板深度融入知识库设计

## 背景

当前聊天输入区虽然已经收敛为单行编排栏，但模板能力仍然残留为一条独立逻辑：

- `QuickActionsBar` 仍保留模板相关入口与状态
- `KnowledgeBaseSelector` 只负责知识库选择
- 模板与知识库在入口、心智、数据流上仍是两套系统

这会带来三个问题：

- 用户会把模板理解为“另一个功能”，而不是会话上下文的一部分
- 模板与知识库会形成重复入口和重复选择心智
- 文书起草场景无法稳定表达“按某模板 + 基于某知识库”这一组合意图

## 目标

- 将模板能力彻底从独立入口中移除，并深度融入知识库体系
- 保持聊天输入区为单行编排栏
- 只保留 3 个高频动作，低频动作统一收纳到“更多”
- 将知识库入口固定在左侧，将更多入口固定在右侧
- 让模板从“一次性快捷动作”升级为“会话级上下文资源”

## 非目标

- 不重做知识库管理页的完整信息架构
- 不在本次设计中扩展新的业务动作种类
- 不改动右侧工作台与消息区的视觉层级
- 不要求一次性重构所有模板数据存储，只要求聊天链路完成融合

## 方案结论

采用 **单一编排栏 + 模板作为知识库资源类型** 的方案。

核心原则：

- 输入区只保留一个统一编排栏
- `知识库` 位于最左侧，承担上下文资源入口
- 中间只保留 3 个高频动作：快速咨询、合同审查、文书起草
- `更多` 位于最右侧，承载低频动作
- 原有 `模板` 入口彻底删除，不再出现在主栏、更多或平行弹层中
- 模板在知识库体系中以“资源类型”的身份存在

最终单行顺序固定为：

1. 知识库
2. 快速咨询
3. 合同审查
4. 文书起草
5. 更多

## 信息架构

### 顶层结构

单行编排栏拆分为三段：

- **左侧上下文入口**
  - 知识库
- **中间主动作组**
  - 快速咨询
  - 合同审查
  - 文书起草
- **右侧收纳入口**
  - 更多

这三段分别回答三个问题：

- 知识库：这次回答基于什么资源
- 主动作：这次我想做什么
- 更多：还有哪些低频能力

### 模板的归属

模板不再归属于主动作，也不再归属于更多，而是归属于知识库体系内部。

其定位从：

- “点击后立即给输入框塞提示词的快捷工具”

升级为：

- “会话上下文中的结构化资源”

也就是说，模板与知识库共同组成“资源上下文”，只是资源类型不同：

- 知识库资源：提供事实、案例、制度、文档范围
- 模板资源：提供输出结构、章节顺序、文书骨架

### 折叠规则

- 桌面端固定单行，不换行
- 主栏只显示知识库、3 个高频动作、更多
- 模板永远不在主栏显示
- 合规风控、法律检索等低频动作进入更多
- 移动端保留同样的左右结构，但主动作可压缩为 2 个

## 知识库入口升级设计

### 从知识库选择器升级为资源选择器

`KnowledgeBaseSelector` 不再只是“添加知识库”，而是升级为统一的上下文资源选择器。

顶部提供资源视图切换：

- 全部
- 知识库
- 模板

用户通过同一个入口完成以下动作：

- 选择参考知识库
- 选择输出模板
- 组合知识库与模板

### 列表项形态

资源列表统一卡片结构，但不同类型保留清晰标识：

- 知识库项显示：
  - 名称
  - 描述
  - 类型 / 来源
- 模板项显示：
  - 模板标识
  - 模板名称
  - 适用场景
  - 简要用途说明

二者在交互层面一致：

- 都支持搜索
- 都支持筛选
- 都支持选中 / 取消选中
- 都进入当前会话上下文

### 入口文案

知识库按钮不再使用“添加知识库”文案，而统一使用状态化表达：

- 未选择任何资源：知识库
- 已选择知识库：知识库 · N
- 已选择模板但无知识库：知识库 · 模板 1
- 同时选中两类资源：知识库 · 资料 N · 模板 M

按钮文案的目标不是列出全部名称，而是表达“当前会话已绑定资源上下文”。

## 交互规则

### 主流程

用户使用链路调整为：

1. 先通过知识库入口选择上下文资源
2. 再选择动作（快速咨询 / 合同审查 / 文书起草）
3. 再补充输入内容
4. 发送消息

### 模板选择后的行为

旧逻辑：

- 点击模板
- 打开模板弹层
- 直接向输入框注入“请基于某模板帮我起草……”

新逻辑：

- 在知识库资源选择器中选中模板
- 模板进入当前会话上下文
- 用户点击文书起草或直接输入需求
- 发送消息时，模板信息与知识库信息一起提交

这样模板不再是一次性动作，而是可持续影响当前会话输出的上下文条件。

### 组合使用规则

- 仅选知识库：代表“回答内容受资料范围约束”
- 仅选模板：代表“输出结构受模板约束”
- 同时选中：代表“按模板输出，并依据知识库内容生成”

### 更多菜单

更多始终位于右侧，不承载模板。

更多只包含低频动作，例如：

- 合规风控
- 法律检索

其职责是动作收纳，而不是资源收纳。

## 组件边界

### `InputOrchestrationBar`

- 继续作为统一单行编排栏容器
- 固定内部顺序为：知识库 → 高频动作 → 更多
- 不承担资源数据处理，只负责编排和布局

### `QuickActionsBar`

- 收缩为纯动作渲染器
- 只负责快速咨询、合同审查、文书起草及更多
- 删除模板按钮
- 删除模板弹层状态
- 删除模板从更多中出现的逻辑

### `KnowledgeBaseSelector`

- 升级为统一资源选择器
- 除知识库数据外，新增模板资源集合
- 管理资源类型切换、搜索、选中态和状态摘要

### `TemplateSelector`

- 退出聊天主链路
- 不再被输入区引用
- 若其他页面仍需模板浏览，可保留底层资源定义，但不能继续作为聊天入口组件使用

### `Chat.tsx`

- 从仅管理 `selectedKbIds`
- 升级为管理统一资源上下文

建议状态至少包括：

- `selectedKbIds`
- `selectedTemplateIds` 或单选 `selectedTemplateId`

如后续希望进一步统一，也可抽象为：

- `selectedResources`

但本次不强制先做底层打平。

## 数据流设计

### 前端状态

需要把当前会话的资源上下文从“仅知识库”升级为“知识库 + 模板”。

最稳妥的方式是分层管理：

- 动作状态：当前高频动作
- 资源状态：知识库、模板
- 输入状态：文本、附件、深度思考等

### 发送协议

为实现真正的深度融合，发送消息时不能只沿用现有的 `knowledge_base_ids`。

建议在聊天发送协议中显式增加模板上下文字段，例如：

- `template_id`
- `template_ids`
- 或更通用的 `resource_context`

第一阶段允许做兼容：

- 前端先完成 UI 与状态融合
- 若后端暂未支持模板字段，可临时保持兼容提示词注入

但最终目标必须是：

- 模板作为会话上下文显式传给后端
- 后端明确区分“资料依据”和“输出结构”

否则仍只是“入口合并”，而不是深度融合。

## 视觉规范

### 编排栏布局

- 单行固定，不允许第二行
- 知识库按钮位于左侧
- 更多按钮位于右侧
- 中间动作区保持最强可见性

### 按钮层级

- 知识库：上下文入口，弱于主动作，强于普通文本提示
- 主动作：最强操作层级
- 更多：弱操作层级，但必须稳定可见

### 样式原则

- 使用既有语义色与 token
- 主动作保持现有圆角胶囊按钮风格
- 知识库与更多保持同一视觉体系
- 不新增第二套模板专属视觉语言

### 文案原则

- 主栏不再出现“模板”
- 知识库入口表达资源上下文，而不是资源管理动作
- 更多只表达收纳，不表达业务类型

## 风险与约束

### 风险点

- 模板如果仍依赖旧的提示词注入链路，可能导致新旧路径并存
- 知识库选择器升级后，列表密度与筛选复杂度会提升
- 如果模板允许多选，需要明确模板与模板之间的优先级

### 约束选择

为控制范围，本次建议：

- 模板先支持单选
- 知识库支持多选
- UI 层统一，数据层先分字段管理

这样能实现深度融合，同时避免一次性重构过深。

## 验证方案

### 功能验证

- 主栏不再出现模板按钮
- 更多中不再出现模板入口
- 知识库入口可查看模板资源
- 模板资源可被搜索、选择、取消
- 选择模板后，文书起草链路能感知模板上下文
- 同时选择知识库与模板时，二者都能参与会话

### 界面验证

- 单行结构稳定，不因状态变化而换行
- 知识库固定左侧、更多固定右侧
- 桌面端仅保留 3 个高频动作
- 暗色 / 亮色模式视觉统一

### 回归验证

- 前端类型检查通过
- 前端 build 通过
- 聊天页输入区在无资源、仅知识库、仅模板、组合资源四种场景下都可正常渲染

## 结论

本次调整不是把模板“搬进知识库弹层”这么简单，而是要完成三层融合：

- **入口融合**：模板不再作为独立按钮出现
- **结构融合**：模板成为知识库体系中的资源类型
- **会话融合**：模板作为上下文参与生成，而不是一次性提示词技巧

最终结果需要满足四个判断标准：

- 输入区只剩一条单行编排栏
- 知识库在左、更多在右、模板从主栏彻底消失
- 用户能在知识库入口中统一选择资料与模板
- 文书生成链路能真正感知“模板 + 资料”的组合上下文
