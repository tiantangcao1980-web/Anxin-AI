# 全局 UI/UX 与 A2UI 统一设计

## 背景

当前前端已经具备主题系统、Tailwind 变量、`design-tokens`、`PageContainer`、A2UI 渲染器等基础能力，但设计系统没有真正收口：

- 标准业务页、聊天工作台、尽调页、知识图谱、后台页使用了不同的布局逻辑
- 标题、间距、卡片、输入框、状态反馈存在多套口径
- A2UI 同时存在主渲染链、core registry、legacy 渲染三套并行实现
- 图谱、后台图表、部分页面仍散落使用蓝紫粉等硬编码颜色
- 聊天内智能结果和独立页面结果没有形成同一套可识别的产品表达

这会导致产品整体视觉不统一、交互预期不稳定、组件复用困难，也让 A2UI 难以成为全站智能体验的核心表达层。

## 目标

- 保留当前品牌橙作为全站视觉基线
- 建立覆盖业务页、工作台页、分析页、后台页的统一 UI/UX 规范
- 将 A2UI 提升为全站智能结果表达协议，而不是聊天专属卡片
- 统一页面层级、反馈模式、操作流和设计令牌
- 让用户在任意页面都能快速识别当前位置、当前状态、可执行动作和下一步路径

## 非目标

- 不在本期重做品牌定位或更换主品牌色
- 不追求营销官网式的大幅视觉实验
- 不同时引入新的组件库或大规模替换前端技术栈
- 不把本次改造扩展为新的信息架构重构或权限系统重写

## 方案结论

采用 **设计系统先收口，再全量落地页面与 A2UI** 的方案。

整体分为四层：

1. **品牌与令牌层**
2. **页面骨架与交互规范层**
3. **A2UI 主协议与组件层**
4. **功能页面落地层**

实施方式上采用一次统一设计语言、分层实现，而不是分散修补页面。这样既满足“全量统一”的目标，也能控制工程风险。

## 一、品牌与设计令牌

### 1. 颜色体系

保留品牌橙为主品牌色，但不再只作为按钮颜色使用，而是扩展为完整语义体系：

- **Brand**：主品牌橙，负责主 CTA、激活态、当前步骤、重点高亮
- **Neutral**：页面背景、分区背景、边框、说明文本、禁用态
- **Info**：信息提示、系统状态、次级引导
- **Success**：完成、通过、低风险、应用成功
- **Warning**：处理中、中风险、待确认
- **Danger**：高风险、阻断错误、危险操作

要求：

- 页面、图表、图谱节点、A2UI 标签、后台报表统一走语义色
- 现有蓝紫粉等硬编码颜色全部收敛为 token 引用
- dark mode 与 light mode 共用同一套语义映射，不允许局部脱离主题体系

### 2. 字体与层级

统一为五级文本体系：

- **Page Title**：页面一级标题
- **Section Title**：区块标题
- **Card Title**：卡片标题
- **Body / Caption**：正文与辅助说明
- **Meta / Tag**：标签、状态、小字说明

要求：

- `PageContainer` 和 `design-tokens` 的标题定义统一到同一口径
- 特化页面不再自行发明标题尺度
- 页面标题和操作区说明始终体现主次关系，而不是靠颜色硬拉层级

### 3. 间距、圆角、阴影

统一定义：

- 页面外边距
- 区块间距
- 卡片内边距
- 表单控件高度
- 面板分割缝隙
- 弹窗、抽屉、悬浮层圆角
- 卡片、浮层、强调区阴影强度

原则：

- 页面信息密度高，但不能拥挤
- 面板与卡片的层次通过背景、边框、阴影共同表达
- 不再通过局部大量不同圆角与阴影制造“拼装感”

### 4. 状态体系

统一全站状态组件与文案结构：

- 空状态
- 加载中
- 流式处理中
- 成功完成
- 失败重试
- 权限不足
- 无结果 / 低相关结果

要求：

- 任意功能页遇到类似状态时，反馈结构和视觉语言一致
- A2UI 的流式状态与独立页面的处理中状态保持一致

## 二、页面骨架与 UX 规范

### 1. 页面模板

统一定义四类页面模板：

#### 标准业务页

适用于合同、案件、文档、知识库、消息列表等。

标准结构：

- 页头：标题、说明、主操作
- 工具栏：筛选、搜索、批量操作
- 内容区：列表、卡片或详情
- 状态区：空状态、加载态、异常提示

#### 工作台页

适用于 Chat、智能工作台、带多面板交互的复合任务页。

标准结构：

- 左侧上下文或历史
- 中央主任务区
- 右侧智能工作台 / 辅助面板
- 顶部统一任务标题与状态指示

#### 分析页

适用于尽调、知识图谱、合同审查等专业分析页。

标准结构：

- 顶部任务摘要与工具区
- 中部主分析画布或结果主体
- 侧边细节、筛选、结构导航或动作区
- 底部可选的总结 / 推荐动作区

#### 后台页

适用于管理、报表、配置、审计、系统状态等。

标准结构：

- 页头：标题、摘要、刷新 / 新建 / 导出
- 内容区：指标卡、图表、表格、配置表单
- 页内二级导航：标签页或左侧分组

### 2. 统一交互节奏

所有页面中的关键流程要遵守同一套节奏：

- 用户先理解当前上下文
- 系统清楚显示当前状态
- 结果输出结构化且可操作
- 操作完成后有明确反馈和下一步建议

典型流程包括：

- 上传 → 解析 → 分析 → 输出 → 保存
- 搜索 → 筛选 → 查看详情 → 执行动作
- 生成 → 流式展示 → 审核 → 应用 / 导出

### 3. 行为一致性

统一以下行为：

- 搜索框位置与交互
- 筛选条布局
- 表单提交与校验提示
- 弹窗与抽屉的确认 / 取消按钮位置
- 主次按钮优先级
- 下载、保存、刷新、重试按钮的反馈方式

## 三、A2UI 统一策略

### 1. A2UI 的角色

A2UI 被定义为全站智能结果展示协议，而不是聊天页的附属组件。

适用场景包括：

- 聊天中的智能输出
- 合同审查结果
- 尽调结果块
- 法规检索推荐动作
- 工作台任务卡片
- 分析型页面中的 AI 辅助模块

### 2. 主协议收口

当前存在主渲染链、core registry 和 legacy renderer 三套实现。本期策略是：

- 以当前实际主用的 A2UI 渲染协议为主线
- legacy renderer 保留兼容层，不再继续扩展
- registry 的命名和主协议对齐
- 后续新增智能卡片一律走主协议

### 3. A2UI 核心组件

本期统一以下核心组件：

- **Recommendation Card**
- **Workspace Card**
- **Streaming Result**
- **Form Sheet**
- **Risk Assessment Card**
- **Action Footer**
- **Status Banner**

统一要求：

- 头部区：标题、来源、状态、主标签
- 内容区：信息摘要、结构化字段、重点高亮
- 状态区：处理中、完成、失败、低可信度提示
- 动作区：主动作、次动作、更多操作

### 4. A2UI 视觉规则

- 卡片密度统一，不因业务来源不同而完全变样
- 风险和建议通过标签、边框、图标、重点文本表达，不靠整块纯色轰炸
- 流式输出统一采用“步骤进展 + 增量结果 + 推荐后续动作”
- 移动端优先保证可读性与动作可触达，而不是强行保留桌面布局

### 5. A2UI 与页面融合

页面级结果区和聊天中的 A2UI 卡片要共用同一套视觉语言：

- 同类结果在不同入口看起来属于同一个产品
- 用户能从聊天页无缝迁移到独立页，不产生认知断裂

## 四、核心页面设计

### 1. Chat / 智能工作台

目标：成为全站最强的智能任务中枢。

设计要求：

- 左中右三栏统一层级和边界
- 输入区、快捷动作、上传态、思考态、A2UI 卡片统一密度与视觉节奏
- 用户始终可见“当前任务、AI 正在做什么、结果在哪、下一步是什么”
- 上传合同、尽调材料、法规问题后，统一进入智能任务流而不是局部临时 UI

### 2. 合同审查

目标：聊天内审查卡片、独立合同审查页、合同管理审查结果共用一套结果表达。

设计要求：

- 风险总览、风险条款、缺失条款、法律依据、修改建议、动作区统一结构
- 流式审查过程具备明确步骤指示
- 审查结果必须是“可消费的”，支持审核、应用、保存、下载

### 3. 尽职调查

目标：从功能集合页升级为结构清晰的分析页。

设计要求：

- 顶部检索与筛选区固定
- 每个分析模块统一为可展开的分析卡
- 结果与建议动作的视觉风格与 A2UI 对齐

### 4. 知识图谱

目标：保留沉浸式画布体验，同时收口外围交互。

设计要求：

- 图谱画布、筛选器、详情抽屉、图例、浮层控制统一使用设计 token
- 节点配色收口到语义体系
- 用户始终能理解当前实体、当前筛选、当前视角和可执行操作

## 五、标准业务页与后台页

### 1. 标准业务页

适用范围：

- Contracts
- Cases / CaseDetail
- Documents
- Messages
- Knowledge Base
- Compliance Check

要求：

- 统一 `PageContainer` 壳层
- 统一列表工具栏、批量操作、空状态、分页交互
- 列表页与详情页的过渡行为一致

### 2. 后台页

适用范围：

- Dashboard
- Billing
- Users
- Roles
- Health
- Feature Flags
- 审计与配置页

要求：

- 后台页仍属于同一品牌体系，只是信息密度更高
- 指标卡、图表、表单、表格共享同一设计系统
- 不再允许后台页单独定义一套颜色和视觉逻辑

- `A2UIRenderer.tsx`

### 第三层：核心页面

### 第四层：标准业务页与后台页

- legacy A2UI 样式与协议残留
- 重复 page shell

- 不再符合规范的局部 preset

## 七、验收标准

### 1. 视觉一致性

- 同类页面标题、间距、卡片、按钮、状态表达一致
- 主品牌橙与语义色使用清晰，没有明显的遗留主色冲突
- dark mode 与 light mode 都保持统一层级和品牌识别

### 2. 交互一致性

- 上传、分析、生成、保存、下载、失败反馈的流程结构一致
- 用户在任意页面都能快速理解当前状态和下一步动作
- A2UI 在聊天中与独立页面中的表达规则一致

### 3. 工程一致性

- 新样式优先走 token 和公共组件
- legacy 仅保留兼容，不再继续成为主扩展点
- 页面级重复样式显著减少

### 4. 产品体验一致性

- 用户能识别这是同一个产品，而不是多个子系统拼接
- 智能结果在页面内是可阅读、可比较、可操作、可落地的

## 八、实施策略

虽然目标是全量统一，但工程实施采用分层推进：

1. **先收口设计系统基础**
2. **再统一 A2UI 主组件**
3. **优先改造 Chat、合同审查、尽调、知识图谱**
4. **再批量套用到标准业务页和后台页**
5. **最后清理遗留样式与协议**

这样可以保证统一设计语言一次到位，同时避免直接全站散改带来的不稳定。

## 九、风险与约束

- Chat、知识图谱、尽调页属于高复杂度页面，不能只做表层换肤，必须同步处理信息层级与面板结构
- A2UI 三套实现并行是当前最大一致性风险，必须先明确主协议
- 后台和图谱中的硬编码颜色较多，若不集中治理，后续页面会继续回退到局部定义
- 设计系统落地必须以“全站统一”为目标，不能在核心页面和普通页面之间形成新的双标准
